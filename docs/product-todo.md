> 使用方式：完成一项勾一项；P0 未清空前不发版。

## 结论（先看这段）

- 上架不等于获客。Play 上 "water reminder" 是红海，WaterMinder / Water Time / Plant Nanny 占据搜索前排，新应用没有权重。
- 真实机会只有三类人：讨厌订阅制的（竞品基本都是月费）、隐私敏感 / 讨厌广告的、从 GitHub 或中文社区来的用户。
- 第一版 KPI 不是下载量，而是**次周留存**。功能和体验的排序按「是否影响留存」来定。
- 获客端只做低成本动作，不投广告（这个品类 CPI 打不过头部）。
- 跨端是竞品短期内难以复制的差异，但**只有已经具备的能力才能写进商店描述**（见第 7 节）。

| P0 | 通用 | 多语言适配（排在首次引导之后开发） |

**建议执行顺序**：禁止横屏 → 首次启动个性化引导 → 多语言适配 → 桌面小组件 → 留存功能 → 跨端联动。

## 2. 跨端联动

### 2.1 多端配置与数据同步（P1）

- **目标**：同一份饮水记录、每日目标、提醒配置（间隔 / 时段 / 重复日 / 勿扰 / 音效 / 通知开关）与主题，在 Android 与桌面端之间双向同步，且不引入账号体系。
- **为什么是卖点**：竞品几乎都是纯移动端。「电脑上记一杯，手机上立刻看到」只有跨端产品做得到，同时解决留存与换机两个问题。
- **待办**：
  - [ ] 先定传输方案（见「待决策」）：局域网直连 / 自选云盘。
  - [ ] 局域网方案：同 WiFi 下 mDNS 发现 + 二维码配对，本地 HTTP / WebSocket 传输，数据不出内网。
  - [ ] 自选云盘方案：WebDAV / S3 兼容存储，用户自己填地址与凭据，数据不经过开发者服务器。
  - [ ] 提醒共享：约定一台「主设备」负责排期与弹窗，其他端只展示同步后的下一次提醒时间，避免两台设备同时提醒。
  - [ ] 冲突策略：饮水记录按 `requestId` 幂等合并（复用现有去重机制）；每日总量按条目合并，不按总量覆盖；配置按 `updatedAt` 后写入者优先，并带版本号防回环。
  - [ ] 断网时本地功能照常可用，恢复后自动补同步。
- **注意**：现有导入是「只补缺失日期、不覆盖」，直接拿来做同步会丢数据，必须单独实现合并逻辑。
- **上线顺序**：先补齐导出 / 导入体验（已有），再做局域网配对，最后考虑云盘。
- **隐私影响**：局域网方案不改变隐私政策；若接云盘，隐私政策需说明「数据存储于用户自选的第三方」。
- **验收**：两端配对后，任一端记录饮水或改提醒配置，另一端 5 秒内生效；重复同步不产生重复记录；同一时段只有主设备弹提醒。

## 3. 通用功能与留存

### 3.1 数据备份提示（P2，优先级已下调）

- [ ] 首次达标后（或连续使用 7 天）提示做一次 JSON 备份，入口指向「我的 → 数据备份」，可关闭不再提示。
- [ ] 提示只出现一次；从「我的」可随时导出 / 导入。
- **现状**：数据只在本机，换机即丢。无账号是卖点，但用户丢一次数据就是 1 星。
- **为什么下调**：它影响的是长期偶发事件，不解决首日卸载；上架前的阻塞项是引导与语言。设计保留，等留存功能做完再顺手实现。

### 3.2 连续达标天数（streak）+ 里程碑（P1）

- [ ] 基于每日总量与当日目标计算连续达标天数；今日页进度环下方展示「连续 N 天」。
- [ ] 7 / 30 / 100 天给一次性视觉反馈。
- **注意**：小组件快照已预留 `streak` 字段，计算逻辑放在 Rust 侧统一出口，避免前后端各算一套。

### 3.3 规则版目标推荐（P2）

- [ ] 按体重 + 活动量给出推荐值，引导用户设置，并说明计算依据；不做医疗宣称。
- **现状**：只有一行固定文案「建议每天 1500~1700ml」。

### 3.4 周报 / 洞察卡片（P2）

- [ ] 「你周三最容易漏」「下午喝得最少」这类基于已有数据的轻洞察，放在数据页顶部，让用户有理由回来看。

### 3.5 Health Connect 写入（P2，可选）

- [ ] 能进健康生态，但合规成本高（数据安全表单、隐私政策都要改），不建议第一版做。

### 3.6 邮箱反馈入口（P2）

- **方案**：参考 Easy China 的 `china_travel_essentials/lib/services/feedback_service.dart`。主路径用 `mailto:` 拉起系统邮件客户端并预填主题与正文，不建后端、不自动上传；无邮件客户端时在页面兜底「复制邮箱地址」，不谎报发送成功。
- **待办**：
  - [ ] 新增统一的反馈服务封装：收件地址 `hey47_zhang@163.com`、固定英文主题 `Shui - User Feedback`、分类标签（General / Bug Report / Feature Request / Translation Issue / Other）同样固定英文，界面显示文案可本地化。
  - [ ] 正文只放用户主动填写的内容 + App 版本 + 平台与系统版本（只取首段，不带完整 build 指纹）+ 当前语言；不含设备标识、广告 ID、位置与账号。正文长度上限 4000 字符。
  - [ ] 拉起结果区分 `opened / noMailApp / failed` 三种，分别提示；`noMailApp` 与 `failed` 提供复制邮箱兜底。
  - [ ] 入口接到桌面端 [about/page.tsx](../src/app/setting/about/page.tsx) 与安卓 [me-tab.tsx](../src/components/mobile/me-tab.tsx) 的「反馈与联系」区，替换当前只能复制的静态邮箱。
- **注意**：安卓端需先验证 `mailto:` 经 Tauri opener 或原生 Intent 是否能被系统邮件 App 正常处理，不能处理时直接走复制兜底；不要用 Crashlytics 写日志冒充「提交成功」。
- **验收**：两端点击「邮箱反馈」能拉起邮件 App 且主题正文已预填；设备无邮件 App 时提示并提供一键复制邮箱。

## 7. 跨端差异化：能写什么、不能写什么

**已经实现、可以立即写进商店描述的真实差异**：

| 端 | 独有能力 |
| --- | --- |
| Android | 全屏提醒页、通知栏一键记水、后台可靠性引导（自启动 / 电池优化） |
| macOS / Windows / Linux | 系统托盘倒计时、全局快捷键、会议应用白名单自动暂停、静默开机自启、息屏锁屏自动暂停 |
| 全平台 | 同一套饮水记录与统计口径、相同的 CSV / JSON 导入导出格式 |

**尚未实现、暂不可写进商店的**：多端配置同步、云备份、账号体系、AI 建议、桌面小组件。

> Google Play 要求商店描述与实际功能一致。把未实现的功能写进 listing 会被判定为误导性元数据（Misleading metadata），轻则审核驳回，重则账号受限。因此新功能的文案先准备好、存着，等代码上线后再替换，不要提前提交。
