# 产品待办：上架前与留存功能

> 来源：2026-11-19 的产品评估结论。用途：后续开发按优先级推进，完成一项勾一项。
> 相关文档：[安卓桌面小组件设计](./android-widget-todo.md)、[Google Play 上架材料](./play-store/listing.md)

## 结论（先看这段）

- 上架不等于获客。Play 上 "water reminder" 是红海，WaterMinder / Water Time / Plant Nanny 占据搜索前排，新应用没有权重。
- 真实机会只有三类人：讨厌订阅制的（竞品基本都是月费）、隐私敏感 / 讨厌广告的、从 GitHub 或中文社区来的用户。
- 因此第一版的 KPI 不应是下载量，而是**次周留存**。功能和体验的排序也按「是否影响留存」来定。
- 获客端只做低成本动作，不投广告（这个品类 CPI 打不过头部）。
- 跨端是竞品短期内难以复制的差异：同一套数据模型跑在 macOS / Windows / Linux / Android。但**只有已经具备的能力才能写进商店描述**，未实现的同步不能提前宣称（见「跨端差异化」一节）。

## P0 上架前必须完成

### 1. App 内英文界面（i18n）

- **现状**：`src` 下没有任何 i18n 方案，界面文案全部硬编码中文；但商店默认语言定为 en-US。
- **影响**：英文用户打开即见中文界面，几乎必然卸载，还会拉低评分。这是上架前最大的硬伤。
- **做法**：
  - 引入轻量词典（自建 dictionary + Context 即可，不建议引入 next-intl；桌面端复用同一套）。
  - 先做 `en` / `zh-CN` 两种，默认跟随系统语言。
  - 覆盖范围：移动端各 tab、全屏提醒页、设置页、toast 文案。
  - **原生侧同步**：`ReminderReceiver.kt` 的通知标题 / 副标题 / 按钮文案也必须跟随系统语言，只翻前端会导致英文用户看到中文通知。
- **验收**：系统语言为英文时，App 内与通知文案全为英文；切回中文冷启动后恢复中文。

### 2. 首次启动引导

- **现状**：首屏直接是进度环 + 记录卡片，新用户不知道要先设目标、设间隔、授权通知。
- **做法**：3 步引导（目标 → 提醒间隔 / 生效时段 → 通知权限），每步可跳过，结束后落到今日页。
- **验收**：全新安装后能在 1 分钟内完成配置并收到第一条提醒；第二次启动不再出现。

### 3. 数据备份提示

- **现状**：数据只在本机，换机即丢。无账号是卖点，但用户丢一次数据就是 1 星。
- **做法**：首次达标后（或连续使用 7 天）提示做一次 JSON 备份，入口指向「我的 → 数据备份」，可关闭不再提示。
- **验收**：提示只出现一次；从「我的」可随时导出 / 导入。

## P1 留存（决定 D7）

### 4. 桌面小组件（最高优先）

- 已有独立设计文档，直接按 [android-widget-todo.md](./android-widget-todo.md) 实现，不在此重复。
- 它同时解决「记水要打开 App」和「不打开就被遗忘」两个问题，是这类产品唯一的结构性优势。
- 若只做一件事，做这个。

### 5. 连续达标天数（streak）+ 里程碑

- **现状**：只有「达标天数」统计，没有激励回路。
- **做法**：基于每日总量与当日目标计算连续达标天数；今日页进度环下方展示「连续 N 天」；7 / 30 / 100 天给一次性视觉反馈。
- **注意**：小组件快照里已预留 `streak` 字段，计算逻辑放在 Rust 侧统一出口，避免前后端各算一套。

### 6. 通知增加「稍后提醒」

- **现状**：通知最多 3 个按钮，已被三档水量占满，注释明确写了不放「稍后再说」（见 `ReminderReceiver.kt` 约 1146 行）。
- **做法**：改为 2 个水量 + 1 个「稍后 10 分钟」；稍后需要重新排一个一次性闹钟，且不能打乱既有节奏锚点。
- **注意**：安卓端通知按钮最多 3 个是硬约束，不要试图放 4 个。

### 7. 自定义杯量

- **现状**：首页固定 50 / 100 / 200 / 300 ml，但实际杯子 350 / 500 ml 很常见，记不准用户就不记了。
- **做法**：允许用户在设置里增删改快捷水量（2–4 个），首页、通知栏 Action、小组件共用同一份配置。
- **验收**：改配置后首页、通知、小组件三处水量一致。

### 8. 跨端配置与数据同步

- **目标**：同一份饮水记录、每日目标、提醒配置（间隔 / 时段 / 重复日 / 勿扰 / 音效 / 通知开关）与主题，在 Android 与桌面端之间双向同步，且不引入账号体系。
- **为什么是卖点**：竞品几乎都是纯移动端。「电脑上记一杯，手机上立刻看到」只有跨端产品做得到，同时解决留存与换机两个问题。
- **方案方向（实现前先定）**：
  - 局域网直连：同 WiFi 下 mDNS 发现 + 二维码配对，本地 HTTP / WebSocket 传输，数据不出内网。
  - 自选云盘：WebDAV / S3 兼容存储，用户自己填地址与凭据，数据不经过开发者服务器。
  - 不建议自建账号 + 云端：会破坏「无账号、隐私优先」的定位，也增加合规成本。
- **冲突策略**：饮水记录按 `requestId` 幂等合并（复用现有去重机制）；每日总量按条目合并，不按总量覆盖；配置按 `updatedAt` 后写入者优先，并带版本号防止回环。
- **注意**：现有导入是「只补缺失日期、不覆盖」，直接拿来做同步会丢数据，必须单独实现合并逻辑。
- **上线顺序**：先补齐导出 / 导入体验（已有），再做局域网配对，最后考虑云盘。
- **隐私影响**：局域网方案不改变隐私政策；若接云盘，隐私政策需说明「数据存储于用户自选的第三方」。
- **验收**：两端配对后，任一端记录饮水或改提醒间隔，另一端 5 秒内生效；重复同步不产生重复记录；断网时本地照常可用。

## P2 差异化（留存之后再做）

### 9. 目标推荐

- **现状**：只有一行固定文案「建议每天 1500~1700ml」。
- **做法**：按体重 + 活动量给出推荐值，引导用户设置，并说明计算依据；不做医疗宣称。

### 10. 周报 / 洞察卡片

- **做法**：「你周三最容易漏」「下午喝得最少」这类基于已有数据的轻洞察，放在数据页顶部，让用户有理由回来看。

### 11. Health Connect 写入（可选）

- 能进健康生态，但合规成本高（数据安全表单、隐私政策都要改），不建议第一版做。

## 跨端差异化：能写什么、不能写什么

**已经实现、可以立即写进商店描述的真实差异**（代码里都跑得通）：

| 端 | 独有能力 |
| --- | --- |
| Android | 全屏提醒页、通知栏一键记水、后台可靠性引导（自启动 / 电池优化） |
| macOS / Windows / Linux | 系统托盘倒计时、全局快捷键、会议应用白名单自动暂停、静默开机自启、息屏锁屏自动暂停 |
| 全平台 | 同一套饮水记录与统计口径、相同的 CSV / JSON 导入导出格式 |

**尚未实现、暂不可写进商店的**：多端配置同步、云备份、账号体系。

> Google Play 要求商店描述与实际功能一致。把未实现的功能写进 listing 会被判定为误导性元数据（Misleading metadata），轻则审核驳回，重则账号受限。因此同步功能的文案先准备好、存着，等代码上线后再替换，不要提前提交。

**文案准备**：中英文「跨端」段落与「同步」段落已写入 [listing.md](./play-store/listing.md)，其中同步段落放在文末「待启用文案」里，实现后直接替换完整说明中的对应段落。

## 体验优化清单（小改动，随版本顺手做）

- [ ] **数据页的「提醒记录」折叠或移到「我的」**。触发 / 确认 / 跳过 / 超时 / 展示时长是开发者视角的数据，对普通用户是负价值，占了注意力（`src/components/mobile/data-tab.tsx`）。
- [ ] **30 天趋势加「本周 vs 上周」对比**。现在必须横滑，纵轴按目标取整，跨周对比很弱。
- [ ] **达标动效**。现在只有 toast + 通知，进度环应有一次完整的完成动画。
- [ ] **撤销改为 toast 内撤销**。现在二次确认弹窗打断了高频操作（`today-tab.tsx` 的 undo 流程）。
- [ ] **全屏提醒加「稍后」**。现在只有记录 / 跳过（`src/components/mobile/fullscreen-reminder.tsx`）。
- [ ] **通知按钮折叠问题**。部分 ROM 会把 3 个按钮收进展开态，首次使用时在引导里说明，避免用户以为没有记录入口。
